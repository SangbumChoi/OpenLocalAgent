# Why planning and acting are different (and why we keep them apart)

> Companion to [`COMPUTER_USE_DEBATE.md`](./COMPUTER_USE_DEBATE.md) and experiment **17** in
> [`EXPERIMENTS.md`](./EXPERIMENTS.md). The debate concluded a sub-100M agent should buy
> *composition* with a **planner over grounded calls** (`ToolCaller.plan()`), not an interpreter.
> This file answers the follow-up question: *why is planning a different operation from acting at
> all* — phrased, as asked, in terms of the model's **logit distribution**, and grounded in the
> numbers we actually measured.

---

## 1. The measurement that frames everything

We teacher-forced 240 held-out single-call tool bodies through the trained 28M byte model and split
every generated byte into two classes — the **structural** bytes (the JSON scaffolding, keys, and
tool name: `{"arguments":{"city":"`…`"},"name":"get_weather"}`) and the **slot-value** bytes (the
copied argument, e.g. a held-out city). The model's *own* next-byte distribution looks completely
different at the two:

| position class | mean next-byte entropy | top-1 (free-gen) accuracy | copy-mass on prompt bytes |
|---|---|---|---|
| **structural** | 0.18 bits | 96.6% | 57.7% |
| **slot-value**  | 3.28 bits | 23.7% | **74.9%** |

Read this as a statement about *where the information lives*:

- **Structural bytes are in the weights.** They are in-distribution (every training example had the
  same scaffolding and the same finite set of tool names), so the distribution collapses to ~0.18
  bits — the model is effectively *certain*. This is a **commitment** regime: low entropy, argmax is
  right.
- **Slot-value bytes are in the prompt, not the weights.** The eval value is disjoint from training,
  so the model genuinely cannot know it — 3.28 bits of entropy, argmax wrong ~76% of the time. But
  three-quarters of the probability mass sits on byte values that *appear in the prompt*. The answer
  is reachable; it just isn't the argmax. This is a **copy** regime: the right move is to point at
  the prompt, not to sample the weights.

Grounded decoding wins (100% vs ~1%) precisely because it uses the weights where they're certain
(structure) and *bypasses* them where they're uncertain (copy the slot from the prompt). That is the
whole mechanism behind experiment 01.

**Now apply the same lens one level up.** Acting and planning are two *more* regimes, and they have
the same kind of distributional signature — different enough that asking one tiny forward pass to do
both is a mistake.

---

## 2. Acting is a low-entropy commitment

A single grounded **act** — `caller.call(query)` — is two sub-decisions, and *neither* should be
high-entropy once the inputs are fixed:

1. **Select** one tool. Over a fixed turn this is a classification; the tool-selection head's logits
   should be sharp (one tool dominates). When they aren't, that's the *selection* bottleneck we
   measured elsewhere (figs 12, 14) — and the fix is a re-ranker/retriever, i.e. *more* structure,
   not a softer distribution.
2. **Fill** each argument by a typed, schema-constrained copy. As §1 shows, the *content* of a slot
   is high-entropy in the weights — so we don't let the weights decide it; the schema decoder copies
   the typed span from the prompt. The act's *form* is fully determined by the schema.

So acting is **invariant-poor and precision-critical**: every byte of the emitted call must be
exactly right (a single wrong slot byte breaks the call), and the correct output is a near-delta
distribution — one tool, one typed span per argument. The job is to *remove* entropy: from the
weights where they're confident, from the prompt where they're not. Acting is local (it depends on
*this* turn), and it is unforgiving (exact match).

---

## 3. Planning is a high-entropy segmentation

A **plan** — `caller.plan(query)` — is a different operation with a different distribution:

- Its unit is not a byte or a tool, it is a **sub-goal boundary**. The decision is "where does step 1
  end and step 2 begin, and in what order do they run" — a segmentation over the request's
  *connectives and dependencies* ("read the file **then** run the tests **and** commit"), not over
  the content of any single call.
- It is **paraphrase- and permutation-tolerant at the clause level**. "Read X then test, then
  commit" and "After reading X, run the tests; finally commit" should yield the *same* plan. A good
  planner is *invariant* to surface form — the opposite of acting, which must reproduce surface form
  exactly.
- Its natural distribution is **legitimately higher-entropy**: there can be several valid
  decompositions and orderings of the same request (WebArena's lesson — reward the *outcome*, not one
  trajectory). Collapsing that to a single delta too early is *wrong*; the planner should keep
  options open and let the actor commit.

In distributional terms: where acting wants to *minimize* entropy and land on a delta, planning
operates over a *coarser* alphabet (steps, not bytes) and is healthy when it stays *flat* across
equivalent decompositions. They pull in opposite directions.

---

## 4. Why not do both in one forward pass

Put §2 and §3 together and the conflict is concrete:

| | acting | planning |
|---|---|---|
| unit | byte / tool | sub-goal boundary |
| target distribution | near-delta (commit) | broad over valid decompositions |
| surface form | must reproduce exactly | must be invariant to it |
| context | local (this turn) | global (whole request + dependencies) |
| failure mode | one wrong byte → wrong call | wrong split/order → wrong sequence |
| right pressure | *remove* entropy | *preserve* equivalent options |

One set of weights asked to be **simultaneously** delta-sharp (commit an arg) and broad-invariant
(explore decompositions) is being optimized against itself. At billions of parameters you can
absorb that tension — UI-TARS/CodeAct let a big model do plan+act end-to-end. At **<100M params on a
CPU**, capacity is the scarce resource (it's exactly what makes the *confusable-tool* selection
errors of figs 09/14 unfixable by data alone). Spending that capacity on a head that must hold two
opposed objectives is the worst possible allocation.

This is the real, mechanistic reason the literature separates the two — OctoTools' planner ⟂
executor split beat AutoGen by ~10.6%; AutoGen's planner/executor/critic roles localize errors;
SeeAct splits "say what you want" (plan) from "ground it to an element" (act). It isn't an
engineering nicety; it's that **plan and act have different entropy targets**, and a separator lets
each be specialized and debugged independently.

---

## 5. What we actually built, and why it's the right shape

`ToolCaller.plan()` is the minimal honest realization of this split for a tiny model:

```python
plan = caller.plan("Read src/app.py and run the tests then commit with 'fix'.")
# -> [ToolCall(read_file, {path: "src/app.py"}),
#     ToolCall(run_command, {command: "the tests"}),
#     ToolCall(git_commit, {message: "fix"})]
```

- The **planner** does only the high-entropy job it's good at: segment on connectives
  (`then` / `and then` / `after that` / `and` / `;`) into ordered sub-goals. It commits *nothing*
  about tools or args.
- Each sub-goal is then handed to the **actor** (`call()`), which does only the low-entropy job:
  select one tool, copy the typed args via the schema decoder. Every step is still schema-valid and
  auditable; nothing is free-generated.

So composition (the one thing CodeAct's executable-code action space bought) is captured by
*sequencing grounded acts* — without handing a 30M byte model an interpreter, a sandbox, or a
high-entropy code-generation problem it would fail at for exactly the reason §1 measured. The
planner stays a cheap, deterministic decomposition; the actor stays a constrained copier. Each lives
in the entropy regime it's suited to.

### The through-line, in one sentence
> A tiny model is reliable only when each decision is pushed into the entropy regime it can win —
> *commit* where the weights are certain (structure), *copy* where the answer is in the prompt
> (slots), and *decompose* (don't commit) where the request has multiple valid orderings (plans).
> Acting and planning are different because they sit in different regimes; that's why we keep them
> apart, and why the planner sequences grounded calls instead of generating them.

The multi-turn **trajectory** datasets (coding, computer-use, and *planner-then-execute* episodes in
`agent_synth.py`) exist to train and evaluate exactly this seam — the plan→act decomposition, and
the follow-up acts whose arguments are grounded in earlier tool *responses* rather than the user
turn. See experiment 04 (single- vs multi-turn) and the multi-turn eval in `eval/harness.py`.
